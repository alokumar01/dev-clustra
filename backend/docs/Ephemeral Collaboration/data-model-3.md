# Data Model Design (Phase 1)

**Project:** DevClustra

**Document:** Data Model

**Version:** 1.0

---

# 1. Philosophy

The database should represent the business domain, not the UI.

The application revolves around three core entities:

* Session
* Participant
* Message

Every future feature should extend these entities instead of replacing them.

---

# 2. Entity Relationship

```text
                 Session
                     │
      ┌──────────────┴──────────────┐
      │                             │
Participants                  Messages
      │
      └──────────────┐
                     │
               Presence (Future / Redis)
```

Rules

* A Session has many Participants.
* A Session has many Messages.
* A Participant belongs to exactly one Session.
* A Message belongs to exactly one Session.
* A Message is sent by one Participant.

# 6. Relationships

Session

↓

Many Participants

Session

↓

Many Messages

Participant

↓

Many Messages

Messages never embed Participants.

Participants never embed Messages.

Everything is referenced.

---

# 7. Why References?

Bad

```text
Session

messages: [...]
```

Problems

* Huge document
* MongoDB 16MB limit
* Slow updates
* Difficult pagination

Better

```text
Sessions

Participants

Messages
```

Independent collections.

Unlimited growth.

---

Participant

↓

Socket IDs

---

Socket ID

↓

Participant

---

↓

---

---

# Final Principle

The database exists to model the domain.

The domain is:

Session

↓

Participants

↓

Messages

Everything else—Socket.IO events, APIs, React state, Redis, and UI—is built on top of this model.

A stable domain model means the application can grow from a simple temporary chat into a complete real-time collaboration platform without requiring a fundamental redesign of the database.
